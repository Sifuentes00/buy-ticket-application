### Тип приложения
Разрабатываемая система является **клиент-серверным веб-приложением** с REST API.  
Frontend — одностраничное приложение (SPA) на React, Backend — REST сервис на Spring Boot. Система использует централизованную аутентификацию через Keycloak.

### Стратегия развёртывания
Система развёртывается в виде набора **Docker-контейнеров**:

- **Frontend**: React-приложение (Vite)  
- **Backend**: Spring Boot REST API  
- **Аутентификация**: Keycloak  
- **База данных**: PostgreSQL  

Каждый компонент независим и может масштабироваться отдельно. Контейнеризация упрощает развертывание и поддержку, а также позволяет легко масштабировать отдельные части системы.

### Выбор технологий

| Компонент | Технология | Обоснование |
|------------|-----------|-------------|
| Backend | Spring Boot | REST API, высокая поддержка безопасности, простота интеграции с базой данных, наличие готовых инструментов для тестирования и разработки |
| Frontend | React + Vite | SPA с динамической загрузкой данных, быстрая разработка интерфейсов, поддержка современных UI-библиотек |
| Аутентификация | Keycloak | Централизованная авторизация и аутентификация, поддержка ролей и JWT, упрощение управления безопасностью |
| База данных | PostgreSQL | Надёжная реляционная СУБД с поддержкой транзакций, сложных запросов и индексации данных |

### Показатели качества

- **Масштабируемость**: возможность увеличивать количество экземпляров frontend и backend без изменений архитектуры  
- **Безопасность**: централизованная аутентификация через Keycloak, поддержка ролей и токенов JWT  
- **Производительность**: минимальная нагрузка на фронтенд (SPA), эффективные REST-запросы к backend  
- **Поддерживаемость**: чёткое разделение слоёв Controller → Service → Repository → Entity  
- **Расширяемость**: новые функциональные модули интегрируются через сервисный слой без изменения базовой структуры  

### Сквозная функциональность

- **Аутентификация и авторизация**: Keycloak + JWT, применяется ко всем защищённым endpoint  
- **Логирование**: централизованное логирование всех сервисов и контроллеров backend  
- **Обработка ошибок**: глобальный обработчик исключений в Spring Boot  
- **Валидация данных**: осуществляется на уровне DTO и контроллеров  

### Реальная архитектура (As Is)

Сгенерированные диаграммы классов (или текстовая схема) на основе текущего кода проекта:

**Controllers:**  
- MovieController  
- UserController  
- AuthController  

**Services:**  
- MovieService  
- UserService  
- AuthService  

**Repositories:**  
- MovieRepository  
- UserRepository  

**Entities:**  
- Movie  
- User  
- Role  

**Other:**  
- KeycloakIntegration (SecurityConfig, JWTFilter)  

**Отличия от идеальной архитектуры:**

- В некоторых местах бизнес-логика смешана с контроллерами  
- Отсутствует DTO слой, frontend получает Entity напрямую  
- Логирование не централизованное, обработка ошибок локальная  
- Взаимодействие с Keycloak частично реализовано в контроллерах  

### Сравнение и улучшения

| Пункт | Идеальная архитектура | Реальная архитектура |
|-------|---------------------|--------------------|
| Слои | Controller → Service → Repository → Entity | Иногда бизнес-логика смешана с контроллерами |
| DTO | Используются DTO для передачи данных | DTO отсутствуют, передаются Entity напрямую |
| Сквозная функциональность | Централизованное логирование, обработка ошибок | Локальное логирование и обработка ошибок |
| Безопасность | Keycloak через фильтры, все слои защищены | Частичная интеграция, часть проверок в контроллерах |

**Причины отличий:**  
- MVP реализации для первого спринта  
- Ограничение времени на разработку  
- Отсутствие необходимости полного разделения слоёв на этапе прототипа  

**Пути улучшения:**  
- Ввести DTO и мапперы для отделения модели от API  
- Централизовать обработку ошибок и логирование  
- Чётко разделить Controller и Service для соблюдения принципов SOLID  
- Улучшить интеграцию Keycloak с использованием фильтров и AOP  
- Рассмотреть применение архитектурных шаблонов Layered и MVC  

### Вывод

- Идеальная архитектура обеспечивает высокую поддерживаемость, безопасность и масштабируемость  
- Реальная архитектура соответствует To Be в основном, но требует рефакторинга слоёв, введения DTO и централизованного логирования  
- После внесения улучшений система станет более поддерживаемой, расширяемой и безопасной
